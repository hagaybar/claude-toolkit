## Quirks summary

| Quirk | Severity | Detail |
|---|---|---|
| Loan create: query vs body | MEDIUM | `POST /users/{id}/loans` requires `item_barcode` OR `item_pid` (mutually exclusive) AND optional `user_id_type` as **query params**, while `library` and `circ_desk` go in the **body** as `{"value": "<code>"}` wrapper dicts. Sending all of them as flat body fields, or all of them as query params, is rejected. Skipping `library`/`circ_desk` in the body is also rejected — Alma can't derive defaults from API-key context. |
| Patron expired blocks loans | LOW | `POST /users/{id}/loans` returns 400 + `alma_code 401168` "Patron's card has expired" if the patron's expiration is in the past. This is a server-side rule, not a wrapper bug. Test fixtures need periodic expiration refresh via Alma staff UI or via `update_user`. Plan for it: a SANDBOX test user that worked last quarter may not work this quarter. |
| Loan op endpoint is renew-only | LOW | `POST /users/{id}/loans/{loan_id}` accepts ONLY `op=renew`. There is no `op=return` / `op=lost` etc. on this endpoint — those workflows live on the items resource or on dedicated request flows. |
| Cancel user-request requires `reason` | MEDIUM | `DELETE /almaws/v1/users/{user_id}/requests/{request_id}` is the documented "cancel" path (NOT a `op=cancel` post). The `reason` query param is `required: true` in the swagger; `note` is optional. Returns HTTP 204 No Content (no body). What `GET` on the same request_id returns after cancel is untested (corrected 2026-11-12, see evaluation US-32: this said `alma_code 401129` "Request not found", but per the swagger 401129 is "No items can fulfill the submitted request" on create). Older issue text described `reason` as optional; the swagger contradicts that, swagger wins. |
| User-request create: undocumented `holding_id` | LOW | The toolkit's `create_user_request` accepts a `holding_id` query param per its original spec, but the public Alma swagger only documents `mms_id` and `item_pid` as resource-identifier query params on `POST /users/{id}/requests`. `holding_id` may or may not work depending on Alma version. Prefer `mms_id` or `item_pid` for documented behavior; fall back to `holding_id` only for holdings-level holds where Alma accepts it. |
| User notes PUT shape is FLAT list | HIGH | `user_note` on `PUT /almaws/v1/users/{user_id}` must be a flat `List<UserNote>` — sending the wrapped form `{"user_note": [{...}]}` returns HTTP 400 with `Cannot deserialize value of type java.util.ArrayList<com.exlibris.alma.ws.jaxb.userwebservice.UserNote>` (Jackson sees an Object where the schema declares an ArrayList). Modern GETs return the flat shape too (`"user_note": []` when empty). Some older / XML-derived responses use the wrapped form on GET; defensive read paths must tolerate both, but the WRITE path must always emit the flat list. Discovered 2026-05-13 in TAU SANDBOX via the AlmaAPITK `users-notes` chunk; the toolkit fix landed in commit `6094a5d` with R10 regression at `tests/unit/regressions/test_issue_119_user_note_write_shape.py`. |
| User PUT rejects legacy GET shapes | MEDIUM | The "Swap All" PUT (`PUT /almaws/v1/users/{user_id}`) validates the incoming body against current Alma rules, which sometimes reject data that GET still returns. Observed: a user with `contact_info.address[0].line2` set but `line1` missing (legacy record from before `line1` became mandatory) GETs cleanly but PUTs fail with `400 "Mandatory field is missing: address line1"`. **Implication for any GET-mutate-PUT workflow on users**: choose test fixtures with complete data; failures of this shape mean the existing user data needs UI-side fixing, not wrapper changes. Discovered 2026-05-13 in TAU SANDBOX alongside the `user_note` write-shape bug. |
| Purchase request: citation_type nests under resource_metadata | HIGH | `POST /almaws/v1/users/{user_id}/purchase-requests` requires the **mandatory** `citation_type` field to live INSIDE `resource_metadata`, not at the root of the body. Per the authoritative schema [`rest_purchase_request.json`](https://developers.exlibrisgroup.com/wp-content/uploads/alma/openapi/schemas/rest_purchase_request.json), the body looks like `{"resource_metadata": {"citation_type": {"value": "BOOK"}, "title": "...", "author": "..."}, "format": {"value": "P"}}`. Putting `citation_type` at the root level returns `alma_code 60280` "Purchase request citation type not valid. [BOOK,JOURNAL]" — confusingly, Alma reports a values-list error instead of a missing-field error. Valid `citation_type.value` codes are **BOOK** and **JOURNAL** (only). |
| Purchase request: format codes are short (P/E, not PHYSICAL/DIGITAL) | MEDIUM | The `format.value` field on `POST /almaws/v1/users/{user_id}/purchase-requests` accepts **single-character codes**: `"P"` (physical) or `"E"` (electronic). Sending `"PHYSICAL"` / `"DIGITAL"` returns `alma_code 60270` "Purchase request format not valid: [E,P]". ⚠ This short code is **purchase-request-specific** — do NOT extend it to user-side resource-sharing (borrowing) requests, whose `format` uses the LONG-form codes `PHYSICAL` / `DIGITAL`. Sending `P`/`E` on the RS endpoint returns a mangled `Invalid field value … Value: {1}` error instead of `60270`. Verified SB 2026-07-19. |
| Purchase request: `material_type` is not a real field | LOW | The toolkit's older example bodies referenced `material_type: {"value": "BOOK"}` at the root of purchase-request POST bodies. That field is **not** in the authoritative `rest_purchase_request.json` schema and is silently ignored by Alma (no error, no effect). The material/format intent is carried via `format` (P/E) at root + `requested_type` (PhysicalMaterialType code) when `format.value == "P"`. |
